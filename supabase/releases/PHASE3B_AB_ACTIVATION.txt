승인 후 순서
1. phase3b-ab-draft.before.verify.sql: 모든 matches_expected=true 확인.
2. 동시 함수/권한 관리 작업을 멈추고 phase3b-ab-draft.execute.sql 전체 실행.
   두 함수의 진입부 검사 설치와 draft GRANT는 하나의 BEGIN/COMMIT.
   오류는 전체 실패: ROLLBACK 후 조사. 실패 조건을 건너뛰거나 기존 전체 공개 SQL로 대체하지 않음.
3. phase3b-ab-draft.after.verify.sql: 모든 matches_expected=true 확인.
4. 별도 API 활성화 승인 후 서버 전용 A/B UUID 목록 설정 및 개발 환경의 두 게이트만 개방.
   두 v2, 추천 확정, 햇살, 글, 사진, 구매, 배치는 계속 비활성.
5. 별도 A/B 프로필에서 시작/질문별 저장/새로고침/재로그인 복원 확인.
   자기 답변과 revision만 변경되고 돌봄·원장·잔액은 불변이어야 함.
   같은 계정 두 탭의 revision 충돌은 409, A/B 전환 중 늦은 응답은 폐기.
   운영에 제3의 테스트 사용자를 만들지 않음. 비허용 직접 호출은 로컬 가상 사용자로 검증 완료.

DB 제한

등록은 정확히 2명이어야 하며 검사 함수는 auth.uid()만 사용. 허용 목록 변경은 별도 승인된 SQL로 관리.
검사 함수는 SECURITY INVOKER·빈 search_path·소유자 전용 EXECUTE.
두 공개 RPC는 기존 SECURITY DEFINER·빈 search_path를 유지하며 모든 DML 전에 검사 호출.
UUID는 함수 본문/오류/공개 소스에 없고 비공개 적용 파일의 INSERT와 DB 목록에만 존재.
SQL Editor 실행 이력에도 식별자가 남으므로 프로젝트 관리자만 취급. Git 제외는 암호화가 아님.
