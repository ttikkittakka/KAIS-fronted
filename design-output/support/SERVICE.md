# 지원 제도 신청 도우미 운영 문서

## 접수와 데이터 흐름

1. 사용자가 고른 필요 분야와 연령대, 추천에 사용하는 시·도는 브라우저 메모리에서 처리해요. 추천은 `SUPPORT_PROGRAMS`의 태그를 사용해요. 연령은 순위에 반영하며, 사업별 자격과 모집 여부는 공식 공고에서 확인해요. 기존 정부24 공개 목록 조회에는 로그인 자격 증명과 추천·신청서 데이터가 포함되지 않아요.
2. 사용자에게 선택한 제도, 수집 항목, 기관 제공 범위, 보유 기간을 보여 준 다음 항목별 동의를 받아요. 주소는 시·도와 시·군·구까지만 받고 연락에 필요한 시간대를 골라요. 입력한 신청서는 React 상태에만 있어요. 사연은 별도 동의를 체크한 후 작성할 수 있어요. 사연은 최대 500자이며, 실제 내용과 관계없이 민감정보로 취급해요.
3. `account`의 확인 화면에서 사용자가 제출하면 `getAuthClient()`의 로그인 세션으로 `onestep_support_submit`을 호출해요. 서버는 로그인 계정, 제도 ID, 신청서 필드, 서울 기준 만 19세, 동의 버전을 검증하고 한 트랜잭션에서 신청과 최초 동의 이력을 기록해요. 접수 번호를 재시도에 재사용하며, 같은 입력은 중복 접수되지 않아요. 응답을 받지 못하면 입력을 메모리에 보존해요. 한 번 접수된 내용과 재시도 내용이 다르면 기존 접수를 확인할 수 있도록 알려요.
4. `test`, `preview`, `real`에서는 `appStorage`의 현재 스코프에 접수 번호, 제도 ID, 상태, 접수·종료 일시만 저장해요. 이름, 생년월일, 연락처, 주소, 시간대, 사연과 동의 선택은 기기 저장소에 기록하지 않아요. 모의 접수 이력은 동의 철회 및 정보 삭제 요청 동작으로 지울 수 있어요.
5. 실제 접수 내용은 먼저 운영팀의 처리 대기열에 들어가요. 사용자 화면의 상태는 운영팀의 지원 진행 상태예요. 정부 사이트의 본인인증과 공식 심사·결정은 기관의 절차를 따르고, 사용자는 공식 링크로 직접 신청할 수 있어요.

신청서에는 주민등록번호, 외국인등록번호, 여권번호, 운전면허번호 필드가 없어요. 서버는 정의된 필드만 받아요. 설명과 입력 검증으로 자유 입력에 나타나는 대표 번호 형식을 차단해요. 임의로 변형된 번호도 의심되면 그대로 복사하거나 전달하지 말고 개인정보 보호 담당 절차에 따라 처리해요. 공식 기관이 본인인증이나 추가 서류를 요구하면 사용자가 공식 경로에서 직접 처리하도록 안내해요.

## 동의 버전

동의문과 서버 허용 버전은 `2026-11-19.1`이에요. 처리방침 시행일은 2026년 11월 19일이에요. 동의문 변경 시 사용자 문구, `SUPPORT_CONSENT_VERSION`, 서버의 허용 버전과 테스트를 함께 갱신하고 이전 버전 문구를 보관해요. 기존 동의 이력 행은 당시 버전 그대로 유지해요.

| 체크박스 | 접수 기준 | 기록과 사용 |
| --- | --- | --- |
| 개인정보 수집·이용 (제15조) | 필수 | 접수, 연락, 자격 확인, 신청 지원과 현황 관리 |
| 개인정보 제3자 제공 (제17조) | 필수 | 신청·연계 의사 확인. 실제 제공 전에는 구체적인 기관과 조건에 대해 다시 동의를 받아요. |
| 민감정보 처리 (제23조) | 비어 있지 않은 사연을 보낼 때 필수 | 일반 동의와 별도 동의. 사연은 운영팀의 지원 확인에 사용해요. |
| 진행 알림 수신 | 선택 | 운영팀이 상태 안내에 문자 또는 입력한 이메일을 사용해요. 신청을 위한 연락은 수집·이용의 목적에 포함돼요. |

서버는 접수와 철회를 각각 `submitted`, `withdrawn` 사건으로 추가해요. 사건에는 접수 번호, 동의문 버전, 항목별 선택, 처리 일시가 있고 신청서 본문이나 계정 ID는 없어요. 앱 역할은 원장을 작성·수정·삭제할 권한이 없어요. 서버 함수가 접수·철회 사건을 추가하고 보유 기한이 지나면 접수와 함께 원장이 삭제돼요. [개인정보 보호법](https://www.law.go.kr/lsInfoP.do?lsId=011357), [시행령 제19조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lspttninfSeq=67046).

## 상태와 보유 기간

| 상태 | 의미 |
| --- | --- |
| `received` · 접수 | 운영팀 처리 대기 |
| `reviewing` · 확인 중 | 요건, 모집 여부와 기관 절차 확인 중 |
| `contact_scheduled` · 연락 예정 | 사용자에게 연락할 예정 |
| `completed` · 완료 | 운영팀의 신청 지원 종료 |
| `cancelled` · 취소 | 사용자 또는 운영팀의 지원 중단 |

- 신청을 취소하면 지원을 중단하고 종료 시각을 기록해요. 취소한 신청에서도 동의 철회와 정보 삭제를 요청할 수 있어요.
- 동의를 철회하면 진행 중인 요청은 취소돼요. 같은 트랜잭션에서 계정 식별자, 제도 ID, 신청서 입력값과 알림 설정을 지워요. 신청자 목록과 운영팀 대기열에서도 접수가 사라져요. 계정 연결이 제거된 접수 번호, 상태와 일시, 버전별 동의·철회 이력은 종료일을 기준으로 보관해요. 이미 완료되거나 취소된 요청의 종료일은 유지돼요.
- `public.onestep_support_purge()`는 종료일로부터 1년이 지난 접수와 그 동의 이력을 삭제하고 삭제한 접수 수를 반환해요. 배포 후 신뢰할 수 있는 운영 스케줄러에서 매일 호출해요. 실행 권한은 `service_role`과 DB 소유자에게 있어요. 접수일이 오래됐어도 종료 처리 전의 요청에는 이 기준이 적용되지 않으므로 운영팀이 오래된 대기 건을 확인하고 종결해야 해요.
- 계정 자체를 삭제하면 그 계정에 연결된 접수와 동의 이력도 삭제돼요. Supabase 백업·복제본의 만료와 복원 시 삭제 재적용은 운영 절차에서 별도로 확인해요.

## 운영팀 절차

1. 운영 담당자별 Supabase Auth 계정을 발급하고 승인된 담당자의 사용자 UUID를 확인해요. DB 소유자 역할로 아래처럼 멤버십을 부여하거나 회수해요. 이메일, 앱 설정이나 사용자 메타데이터로 권한을 부여하지 않아요.

   ```sql
   -- Add an approved staff account. Replace the example with the verified Auth user UUID.
   insert into onestep_private.support_staff (user_id)
   values ('00000000-0000-4000-8000-000000000000'::uuid)
   on conflict do nothing;

   -- Revoke the membership of the same account.
   delete from onestep_private.support_staff
   where user_id = '00000000-0000-4000-8000-000000000000'::uuid;
   ```

2. 개인별 직원 로그인 세션으로 `onestep_support_staff_list(p_limit, p_offset)`를 호출해요. 기본 50건, 최대 100건씩 조회해요. 일반 테이블 조회는 자기 신청에 한정돼요. 운영 대기열은 멤버십을 재검사하며, 직원 브라우저에 서비스 역할 키를 넣지 않아요.
3. `onestep_support_staff_set_status(p_id, p_status)`로 처리 상태를 바꿔요. 직원은 대기열에서 연락 가능 시간과 `notify_progress`를 확인해요. `completed` 또는 `cancelled`로 닫힌 접수는 재개하지 않으며, 철회된 접수는 조회·변경 대상에서 빠져요.
4. 운영팀은 사용자에게 연락해 공식 자격과 모집 기간을 확인하고 신청 방법을 안내해요. 실제 기관 소개·제공이 필요하면 받는 기관의 정확한 명칭, 제공 목적·항목, 보유 기간과 거부권을 안내하고 그 기관에 한정한 동의를 남겨요. 기관이 허용하는 범위에서만 위임을 확인하고 대리 지원해요. 기관에 보낼 정보는 안내한 최소 항목으로 제한하고 사연과 고유식별정보는 전달하지 않아요.
5. 연락·제공 직전에도 대기열에서 철회와 취소 여부를 확인해요. 이미 기관에 제공한 건의 정보 권리 요청은 운영팀이 기관에 전달하고 결과를 사용자에게 안내할 수 있도록 실제 기관 연계 절차에 포함해야 해요.

## 실서비스 공개 전 준비

- 앱의 개인정보 보호책임자 자리표시자를 운영 주체, 책임자 성명·직책, 접수 가능한 이메일과 전화번호로 채워요. 열람·정정·삭제·처리 정지, 알림 동의 철회, 대리인 요청과 기관 삭제 요청을 접수·처리하는 절차를 마련해요.
- Supabase 계약상 수탁자, 위탁 계약, 접근 권한·로그, 프로젝트와 백업의 리전 및 만료 정책을 확인해요. 국외 이전이 있다면 근거와 고지·동의 등 필요한 절차를 방침에 반영해요. 호스팅 및 운영 도구에서 신청 본문이 로그나 오류 수집에 남지 않도록 검증해요. [개인정보 보호법 제28조의8](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334953).
- 기관별 연계 협약, 정확한 받는 기관·항목·보유 기간, 적법한 위임과 사용자 재동의 증빙, 실제 전달·회수·파기 확인 절차를 확정해요. 현재 앱과 RPC에는 기관 전송이나 발송 자동화가 없어요. 기관 전송을 시작하기 전에 취소·철회가 연락이나 제공과 겹칠 때의 절차도 검증해요.
- 별도의 운영 대기열 화면, 직원 MFA 및 회수 점검, 조회·제공 감사 기록, 제출과 조회의 요청 제한 및 모니터링, 일일 purge 실행과 실패 알림을 준비해요. 운영자 접근과 권리 요청 절차를 개인정보 보호 담당자가 검토해요.
- 스테이징 Supabase에서 마이그레이션과 환경 설정을 검증해요. 계정 로그인 상태의 실제 브라우저 RPC와 로그아웃·재로그인, 네트워크 실패, 외부 정책 링크, 모바일·키보드 동작을 점검해요. 프로덕션 이전에는 운영팀 담당자와 공식 기관 안내의 최신 내용도 확인해요.

- 서울 청년 마음건강 사업은 서울 거주·연령 기준과 제대군인 예외를 공식 모집 공고로 확인해요. [서울시 청년 마음건강 지원](https://youth.seoul.go.kr/youthConts.do?key=2310100076).
- 생활·주거, 일자리, 학업에는 담당 기관의 공식 링크를 제공해요. [긴급복지지원](https://www.mohw.go.kr/menu.es?mid=a10708010100), [국민취업지원제도](https://www.work24.go.kr/ua/z/z/1300/selectEmssRqutIntro.do), [한국장학재단 국가장학금](https://www.kosaf.go.kr/ko/scholar.do?pg=scholarship05_12_01_01_01p).
